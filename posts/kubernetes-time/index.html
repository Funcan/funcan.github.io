What time? Kubernetes time!

10 July 2026

From time to time I run into a situation where I'd like notes for if I ever hit it again. I've probably got hundreds of text and markdown files with such things, but I thought I'd try to start making them public rather than writing them and mostly forgetting about it. Hopefully some of them prove useful to somebody...

Recently I was trying to debug a situation with a distributed service on K8s and I was becoming more and more convinced that the issue was that one of the nodes had a clock hours off. It turned out not to be the case, but proving that was painful enough that I though I'd have a go at making up something easy to deploy next time.

Back when I build HPC compute clusters, every node ran ntpd, and you could check the time differences between them with ntpdate for debugging. Running daemons in the background on compute clusters that did tightly coupled distributed computations can have some interesting performance issues [^1] but things like time sync are just to critical to not have. ntpd is old and crufty code though, and not at all friendly to run in containers or a non-root environment - it makes assumptions about what you want.

Cloud VMs generally don't to worry about time, the hypervisor takes care of it for you. The AWS EKS images don't have ntpd running, and as mentioned it is painful to run in a container. Thankfully chrony exists as a modern reimplementation of time sync, and it is happy to run in a container and just track offsets rather than trying to fix the system clock. There's even an existing commulity project that queries chrony pods in a deamonset and turns the offsets into grafana metrics - chrony-exporter.

It's easy enough to deploy a daemonset running chrony on every node, then either run a one-shot job to collect the time offsets, or run chrony-exporter to continuously track clock drift.

The daemonset:

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: time-checker
spec:
  selector:
    matchLabels:
      app: time-checker
  template:
    metadata:
      labels:
        app: time-checker
    spec:
      securityContext:
        runAsUser: 1000
        runAsNonRoot: true
      containers:
      - name: chronyd
        image: alpine:latest
        command:
          - /bin/sh
          - -c
          - |
            # 1. Install chrony
            apk add --no-cache chrony

            # 2. Create the unprivileged config
            cat <<EOF > /tmp/chrony.conf
            port 1123
            cmdport 0
            allow all
            local stratum 10
            EOF

            # 3. Run chronyd in the foreground (-d), no clock modifications (-x)
            exec chronyd -d -x -f /tmp/chrony.conf
        ports:
        - containerPort: 1123
          protocol: UDP

We then need a service to expose this to other pods over the network. Since we need to be able to reach each pod individually, not just round-robin between pods, we need a headless service. This means the DNS name for the service will resolve to a list of IPs, one for each pod, rather than a single IP of a load-balancer.

The service:

apiVersion: v1
kind: Service
metadata:
  name: time-mesh
spec:
  clusterIP: None
  selector:
    app: time-checker
  ports:
    - port: 1123
      protocol: UDP

Once these two are applied, we can start querying the time differences. If we wnat a one-shot query, we can use a script wrapped in a kubernetes job such as:

apiVersion: batch/v1
kind: Job
metadata:
  name: time-debug-job
  # A timestamp label helps if you run this frequently
  labels:
    app: time-debug
spec:
  # Optional: Automatically delete the Job and its Pod 10 minutes after it finishes
  ttlSecondsAfterFinished: 600
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsUser: 1000
        runAsNonRoot: true
      containers:
      - name: time-checker
        image: alpine:latest
        command:
        - /bin/sh
        - -c
        - |
          echo "Starting time debug job..."

          # 1. Install dependencies silently
          apk add --no-cache chrony bind-tools > /dev/null 2>&1

          # 2. Discover peers via the Headless Service
          echo "Discovering DaemonSet peers..."
          PEERS=$(nslookup time-mesh.default.svc.cluster.local | awk '/^Address: / { print $2 }' | grep -v ':')

          if [ -z "$PEERS" ]; then
            echo "ERROR: Could not resolve time-mesh.default.svc.cluster.local. Is the service running?"
            exit 1
          fi

          # 3. Build the config
          echo "driftfile /tmp/chrony.drift" > /tmp/query.conf
          for IP in $PEERS; do
              echo "server $IP port 1123 iburst" >> /tmp/query.conf
          done

          # 4. Fire the query and print the matrix
          echo "Gathering microsecond-level offsets across the cluster..."
          echo "--------------------------------------------------------"
          chronyd -Q -u $(whoami) -f /tmp/query.conf

If we want to monitor drift over time then we can install chrony-exporter. This involves adding a sidecar to our chrony daemonset. If you are using a version of k8s new enough to support native sidecar support, it's probably worth using that (change the chroony-exporter container to an initContainer with a restart-policy of always). The following it the new daemonset with the sidecar added:

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: time-checker
spec:
  selector:
    matchLabels:
      app: time-checker
  template:
    metadata:
      labels:
        app: time-checker
      annotations:
        # Standard Prometheus scraping annotations
        prometheus.io/scrape: "true"
        prometheus.io/port: "9123"
    spec:
      securityContext:
        runAsUser: 1000
        runAsNonRoot: true
      containers:
      - name: chronyd
        image: alpine:latest
        command:
          - /bin/sh
          - -c
          - |
            apk add --no-cache chrony

            # Updated Config: cmdport is enabled on localhost for the exporter
            cat <<EOF > /tmp/chrony.conf
            port 1123
            cmdport 323
            bindcmdaddress 127.0.0.1
            allow all
            local stratum 10
            EOF

            exec chronyd -d -x -f /tmp/chrony.conf
        ports:
        - containerPort: 1123
          protocol: UDP

      - name: chrony-exporter
        image: quay.io/superq/chrony-exporter:latest
        args:
          # Tell the exporter to look at the localhost cmdport we just opened
          - "--chrony.address=127.0.0.1:323"
        ports:
        - containerPort: 9123
          protocol: TCP

You may then need to add a ServiceMonitor or PodMonitor depending on your Prometheus operator setup. Something like:

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: time-checker-monitor
  labels:
    release: prometheus-operator
spec:
  selector:
    matchLabels:
      app: time-checker
  namespaceSelector:
    matchNames:
      - default
  endpoints:
    - port: 9123
      interval: 30s

Some there you go. This can be improved - using a proper stripped down image rather than alpine, adding liveness probe to the chrony pods and the exported, wrapping the whole thing in a helm chart, etc, but it's good enough for debugging. I may or may not get round to polishing it some more.
