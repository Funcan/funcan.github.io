A case of small tools

11 July 2026

I've always built small tools to make my life easier. Drilling jigs back when I did factory floor piecework. A bit of code to add getters and setters to java classes back when I was forced to learn java in uni. A tool to list github job runs by parameter values last week. Some of these are single use / throw away, but if I find I've written something twice then I try to keep it around. I've started making these public on github, something I've long aspired to do but rarely got round to. Here are a few of the recent-ish ones:

gh-action-lint

A tool to lint github action workflow files. It started off checking for unpinned actions being used, after the mess with trivy, and has grow a few more checks since around script injection and insecure behaviour with PRs from forks.

https://github.com/Funcan/gh-action-lint

Kubernetes eager OOM killer

Pods in kubernetes won't get OOM killed until the node they're running on experiences memory pressure, even if they're massively over their memory requests and/or limits. This means it is easy to not notice problems with these values until some random future time when some unrelated service causes memory pressure on the node and suddenly your pods are getting killed despite you not having changed anything recently. You certainly can use grafana or similar dashboards to detect this case, but that requires being proactive. This is a small service that monitors container memory usage, and kills pods that are over their memory limits as soon as it notices them. This means you develop a culture of getting these tunables right (or just setting them huge to shut things up) rather than hoping for the best and being surprised later.

https://github.com/Funcan/kubernetes-eager-oom-killer

AWS Snapshot

A tool to create a JSON representation of the state of AWS objects in an account. This can be run regularly as a CRON job, and you can then use diff or similar to see changes over time. This allows you to narrow down the time window where something was created, deleted, upgraded, etc - extremely useful if the account has multiple teams working in it etc. I found this much easier than trying to track changes through terraform logs and such - instead, I can narrow things down to e.g. a 1 hour window, then check what jobs happened in that time - a much smaller search space.

It currently supports:

  • S3 buckets
  • EKS clusters
  • RDS clusters and instances
  • Lambda functions
  • API Gateways
  • DynomoDB tables
  • ELBs
  • SNS queues
  • SQS queues
  • Route53 entries

...and more. Easy to add code for a new resource types, if your requirements are not currently covered.

https://github.com/Funcan/aws-snapshot

Kubernetes Live Images

If you have an image in use on a kubernetes cluster, then letting it get deleted from your docker registry can cause an outage. You don't want to keep all your historical images around forever though. This is a time tool that gathers a list of all of the images in use on a cluster, and pulls their metadata from the docker repository. This freshens the repository's tracking of what is in use, and means if you run this tool e.g. daily you can configure your docker repository to expire anything older than 30 days or some similar value and not risk losing images that are actually in use but haven't needed to be pulled lately.

https://github.com/Funcan/kubernetes-live-images

git who-reviewed

As a platform engineer, I often end up putting up reviews into repos that I don't know the owning team well. This tool will look at the reviewers of previous PRs that touched a given set of files, and give you a suggested list of reviewers to add to your PR, based on the number of reviews of such PRs and their recency.

https://github.com/Funcan/git-who-reviewed

Summary

I find that writing small tools like this is a great way to encode knowledge and experience, and often leads to something that is either directly useful in future or serves as a starting point and discussion point for more tailored solutions. It's also nice to hear somebody having a problem and pull out a tool that just solves it on the spot. I hope some of these can be useful to you, and I'll go through some more in future. Good luck, and I always welcome hearing about tools you've written.

NB I'm not great at remembering to put licenses in all my repos - I've a long standing TODO list item to write a tool to check for basic good practices in my repos like license files, README files, unit tests, linting CI, etc. Maybe you're already of a solution to that? IF so, please drop me a link. Until then, if it helps you for me to clarify the license of any of my repos, please ask - they're all intended to be open source on generous terms.
